- Continuous research loop, phase 2 (ADR 0029, docs/decisions/0029-continuous-research-loop-budget.md). Loop budget path: a trial run with `--rule-ref loop` (`registry.LOOP_RULE_REF`) is charged per run against `research.loop_trials_per_run` (`generator.loop_refusal`: at most that many jobs, no config already in the registry, no retired/screening family, no config a pre-registration queued, never holdout scoring or discovery), NOT against `trial_budget_quarter` (`quarter_trials` skips loop rows; `trial_budget_overrides`/`budget_for` untouched for hand-dispatched trials). Every loop trial is still a registry row, so gates keep RAW K (`n_trials_effective` counts it); cluster K_eff stays information only, K is not frozen at decision time. `cells.plan` refuses a dispatch with more loop cells than the per-run budget. `research-loop.yml` now dispatches `research.yml` with the batch (`gh workflow run`, only the `dispatch` job has `actions: write`, inputs via env, shares `concurrency: research-registry`), skips while a research run is queued or in progress or the batch is empty; the `keepalive` job (`scripts/loop_keepalive.py`, contents: read) fails the run when the last commit on main is over 50 days old, before GitHub disables the schedule at 60. `scripts/research_queue.py` prints the ATR used and the surviving candidates per timeframe. Quant rulings applied: the ATR sizing pre-filter and `research.loop_equity_usd` are GONE (every loop trial runs `--lot-fit`; cells force it); screening and retired families stay out; the grid is widened to pre-declared one-at-a-time dimensions (exits, `session_filter` on 15m/1h, point-in-time `regime_filter`: `goldbot/specialists/loop_filters.py`, applied in every specialist's `candidates`/`candidates_in_context`) and written into the plan as "Loop grid v1"; `research_pass` refuses a loop job that is not a grid member, skips the screen, or lacks `--lot-fit`; `research_queue.py` prints grid size per timeframe (today 15m 0, 1h 14, 4h 11, 1d 11: only tsmom is eligible) and exits 3 with "grid exhausted" (job summary + a weekly comment on #34 from the `exhausted` job, the only one with issues: write); the workflow uses its own `research-loop` concurrency group (not `research-registry`: a cancelled pending run could drop a record job). Not done: cost stress, holdout requirement for loop survivors, health job (phase 3).
