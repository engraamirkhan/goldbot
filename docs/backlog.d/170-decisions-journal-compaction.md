- **170. Compact the decisions journal's small part files off the hot path.** Value: the engines flush the `decisions` journal with `dedupe=False`, one part file per flush (2-16 per 15 min per account), so the table held 9,447 parts / 75 MB on the brain on 2026-11-10 and grows ~600 parts a week per account. R128 narrowed the health pass's read to one account's folder and months, but every other `Store.read("decisions", ...)` (agents/tools.py, the daily review, research) still lists and opens the schema of every part (union_by_name), and each month folder of one account still holds thousands. Acceptance, tests first: a nightly job (never the engine's flush, never the health pass) rewrites each closed month partition (month before the current UTC month) of each source/symbol into one part under the partition's writer lock, written atomically (`Store._write_atomic`: new part first, old parts unlinked only after the rename and fsync; readers hold the shared lock, so none sees both), keeping every row and column exactly (no dedupe: identical journal rows are legitimate), in the stable store order (backlog 162). Because the journal is not deduped, a crash between the rename and the unlinks would leave rows twice on disk: a manifest (`.compact-<id>.json`, fsynced before the rename, naming the replaced parts and the row count) lets the next run (and `Store.read`, which must skip parts a complete manifest replaced) finish the unlinks; a test seeds a partition, stops the job after the rename and before the unlinks, and proves reads and a re-run give every row exactly once; row count and a content hash per partition are logged before and after; the health checks' part-file cache sees the new set and re-reads once. Estimated cost: one read+write of last month's ~2-3 MB per account per night; no Actions minutes.
