# Speeding up development and backtesting: measured, ranked (2026-10-18)

Author: cto. Status: recommendation to the owner; not committed. Safety rails are unchanged by every item below:
RiskGate is the only path to an order, exits are never gated, there is a max of 40 features, `asof_join` stays on
`available_utc`, and every trial is charged to the shared registry.

**What this says.** Backtests are slow because of feature building, not modelling and not hardware. One slow loop,
computed three times per run and again on every dispatch, takes over 90 % of each trial. Tests are slow because
integration runs serially in CI and under CPU and memory contention locally, and because the testmon rule is not
actually installed. The Mac is memory-bound (16 GB, already swapping) before it is CPU-bound.

## 2. Ranked recommendations (impact x effort)

| # | Change | Expected speed-up (basis) | Effort | Risk | Who |
| --- | --- | --- | --- | --- | --- |
| 1 | **Rewrite `f_order_blocks` vectorised or in numba**, with a golden test: identical output on 6 years of 1h and 15m bars. Profile `f_fair_value_gaps`, `f_levels`/`_walk_levels` and `_vol_tercile` next (2.5, 2.7 and 3.5 s). | Trial **52 s → about 18 s (~3x)**. Removing 34.5 of 51.7 s is measured; numba on this loop is typically 50-100x. It applies equally on Actions and on the Mac. | 0.5-1 day (numba is a new dependency: build-vs-buy record, BSD licence, wheels for arm64 and x86) | Low with the golden test. Features feed live models, so quant review is required. | implementer + quant-reviewer |
| 2 | **Build features once per run.** `lookahead_check` returns the full frame it already built, and `_run` reuses it instead of building a third time. | A further **~30 %** off each trial (one of the three builds; measured 47 s across 3 calls) | 2-4 h | Low. The lookahead check itself is unchanged. | implementer + quant-reviewer |
| 3 | **Feature and resample cache keyed on content**: parquet at `~/.cache/goldbot/features/<data digest>/<tf>/<feature_version>-<code hash>.parquet`, with `actions/cache` on the same key in `research.yml`. A cache miss computes, and a hit loads in about 1 s. | Across the 13-run batch, every run after the first per timeframe skips feature building: **about 90 % of trial time** (measured share). Combined with items 1 and 2, the batch drops from **3-7 h to under 1 h**, serially and with no new runners. | 1 day | Medium: a stale cache would silently change results. The key must include the data-v1 digest, the feature version and a hash of `goldbot/features/**`; the registry row records the cache key. | data-engineer (plan) + implementer; quant-reviewer |
| 4 | **Add `pytest-testmon` to `[dev]` and seed `.testmondata`.** This makes the existing lane rule real. | The lane iteration loop goes from minutes to seconds on most commits (98 % fewer tests, measured 2026-10-16 in lane-test-rules). Today the saving is **0**, because the tool is missing. | 1 h | None. The full gates still run once per hand-back. | implementer |
| 5 | **Split CI `backend` into `unit` and `integration` jobs, and shard integration 2-3 ways with a matrix** (free on a public repo, 4-vCPU standard runners). | CI **20 → about 10 min** (backend at 19:47 is the critical path; integration is 77 % of CPU) | 2-4 h | Low. The same tests run, and the required checks are updated to match. | sre/release-manager + implementer |
| 6 | **Local research runner on the Mac, recording honestly**: `scripts/research_local.sh` runs only on a clean checkout at `origin/main` (refused if dirty or ahead). It fetches the registry with `registry_release.sh fetch`, runs `research_pass.py` exactly as `research.yml` does, and saves with `registry_release.sh save` (the existing union and shrink guard). The row records `runner: local-mac`, the git sha and the cache key. Run variants in a `ProcessPoolExecutor` with **at most 3 workers** (1.3 GB peak each for 6 years, an estimated 3 GB for 16 years, and only about 6 GB usable on this Mac). | 3 workers on the performance cores give **about 3x on variant batches**. The bigger gain is no queue: runs start without waiting on the Actions concurrency group. | 1-1.5 days | **Registry race**: the budget check plus write is not atomic across Mac and Actions. Mitigation: the local runner takes the same lock by first dispatching a no-op "hold" run in `research-registry`, or it is allowed only when `gh run list --workflow research.yml --status in_progress` is empty and it re-checks the budget after fetch. Needs a quant-reviewer ruling and an ADR (new persisted-state writer). | architect (ADR), implementer, quant-reviewer, security-reviewer (token use) |
| 7 | **Run variants in parallel within one Actions run** (4 vCPU per runner), using the same ProcessPool code. The single registry write at the end stays. Prefer one dispatch carrying many variants over many dispatches: within a run, variants already share the per-timeframe frames, and it avoids the "pending run cancels pending run" trap. | Up to about 3x on multi-variant runs, after items 1-3 make fitting the larger share | 0.5 day (after item 6) | Low | implementer |
| 8 | **Prune worktrees and make new ones cheap.** Change the prune rule from "used in the last 24 h" to "merged into `origin/main` and no running process"; that covers 112 of 134 today. Create worktree venvs with `uv venv && uv sync` (APFS clonefile from the 5.3 GB uv cache: near-zero disk). Run web checks from the main checkout, never by symlinking node_modules (the 10-17 incident); or adopt pnpm (content-addressed store), which needs a build-vs-buy record. | Reclaims **tens of GB** (67 GB measured by `du`; the true figure is known only after pruning). Lane set-up goes from minutes to seconds. Less disk scanning for Bitdefender. | 2 h | Deleting an active lane's tree; the check for running processes covers that | sre + implementer |
| 9 | **Cut test cost at the source.** (a) Integration fixtures (synthetic releases, `research_pass`) become session-scoped and read-only (throughput-plan item 6a). (b) `test_engine.py` (413 CPU-s, inside `Engine._on_tick`: `_rebuild_bars`, `build_features` and `_write_state` on every tick) gets a smaller bar history in its fixtures now. The production fix (incremental bars, state written on change) is a BACKLOG item with trading-safety review, because it is also tick latency on the live path. | (a)+(b) about 30-40 % of integration CPU (from the 2026-10-16 profile: the 50 slowest tests are 84 %) | (a) 1 day; (b) fixtures 2 h, engine fix 2-3 days | The engine fix touches the money path: full trading-safety review, and exits first stays first (`runner.py:568`) | test-engineer; implementer + trading-safety-reviewer |
| 10 | **Tune local workers to this Mac.** Run an idle baseline with `--durations=25` once. Cap a full gate at 6 performance-core workers (unit 4 + integration 2) and stay at **2 lanes in full gates** (memory, not CPU, is the limit: 578 MB free). Close idle VS Code windows and Chrome tabs while gates run. | Removes the 34-min tail; integration took **4:36 idle vs 34:12 contended** (measured in the gate logs) | 1 h | None | program-director |
| 11 | **Bitdefender exclusions** for `.claude/worktrees`, `.venv`, `~/tmp`, `~/.cache/uv` and `web/node_modules`. | Unmeasured. It uses 45 % of a core at rest, and its cost rises with file opens (imports, `npm ci`, venv builds). Measure one gate run with and without the exclusions before deciding. | 10 min | Reduced scanning of downloaded code. **Owner/IT decision.** | owner |
| 12 | **Agent process.** One dispatch per research batch row, as in item 7. Plan and copy reviews happen before the build (already adopted). Review re-runs only for HIGH/CRITICAL findings. CI must be green before review, so reviewers never re-review after a gate fix. | Fewer round trips (about 40-50 % fewer review invocations, estimated in speed-up-review.md item 5) | Standards text | None | product-owner (AGENT_STANDARDS) |

**Not recommended now: larger GitHub runners.** They are paid per minute even on public repos, and items 1-3 remove
the work instead of buying faster hardware for it. If 15m pooled runs still take more than 20 min after items 1-3, the
CFO prices an 8-core runner for the owner.

## 3. Order of work and how we will know

Week 1: items 4, 10, 1, 2 and 5 (each small, independent and measurable). Week 2: items 3, 8 and 9a. Week 3: the ADR
for item 6, then items 6 and 7. Each item is re-measured the same way: the trial profile (`cProfile` on the same
session_open 2020-2025 command), `gh run view` job times, and the `~/tmp/gates` totals. Targets: **trial ≤ 15 s** on
1h for 6 years, **13-run batch ≤ 1 h**, **CI ≤ 12 min**, **lane gate ≤ 4 min**. These rows go into the ROADMAP
platform section with dates once the program-director slots the lanes.
