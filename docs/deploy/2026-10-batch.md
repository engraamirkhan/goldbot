**Rules for this whole document:**

### 1.4 Install the batch's deploy script (both boxes)
The batch changes `goldbot-deploy` itself (BACKLOG 37-40: aux.db step-back, `--rollback`, the settings check
against the target, the scheduler-job guard). Install it after the security reviewer has signed it off, from the
exact commit you deploy (RUNBOOK 0.5 "Installing a new goldbot-deploy"):

1. **On your Mac** (your own clone, not the box): check the commit is on GitHub's `main`, then note the script's hash at the
   commit you deploy.
   ```bash
   git -C <your goldbot clone> fetch -q origin && git -C <your goldbot clone> show <SHA>:goldbot/ops/linux/goldbot-deploy.sh | shasum -a 256
   git -C <your goldbot clone> merge-base --is-ancestor <SHA> origin/main && echo on-main
   ```
   Without `on-main` (or if `git show` says the commit is unknown), stop.
2. **On the box**, root downloads that commit's copy from GitHub into a root-only folder, checks it against the
   hash from step 1, and installs it only if they match (`sha256sum -c` prints `OK`, otherwise nothing is installed):
   ```bash
   sudo install -d -m 700 -o root -g root /root/goldbot-deploy-new
   sudo curl -fsSL -o /root/goldbot-deploy-new/goldbot-deploy https://raw.githubusercontent.com/engraamirkhan/goldbot/<SHA>/goldbot/ops/linux/goldbot-deploy.sh
   echo "<HASH FROM STEP 1>  /root/goldbot-deploy-new/goldbot-deploy" | sudo sha256sum -c - \
     && sudo install -m 755 -o root -g root /root/goldbot-deploy-new/goldbot-deploy /usr/local/sbin/goldbot-deploy
   sudo rm -rf /root/goldbot-deploy-new
   ```
   Never install it from `/opt/goldbot` or from `sudo -u goldbot git show`. The service user can write that tree and
   its `.git` (`git replace` can swap the file), so a hash computed there proves nothing.

The new script works with the running code: it reads the scheduler state from `scheduler.json` when
`python -m goldbot.db scheduler-status` does not exist yet, and it only reads aux.db's version.

## 5. Rollback plan

**When to roll back, and when not to.** The new code blocks entries whenever something is uncertain. The old code
(OLD_SHA) is known to size the GBP demo wrongly: it treats USD as GBP (ADR 0004, BACKLOG 28).

* **Roll back** when position management or the owner's controls are at risk:
  * an engine or the bridge crash-loops, or reconciliation errors repeat;
  * the dashboard or Telegram cannot start, so you cannot approve or get alerts.
* **Do not roll back** for an entry-only block, such as `fx_conversion_unavailable`, `server_clock_mismatch`,
  `tick_error` that clears, or `market_closed`. Those already stop entries, and exits keep running. Fix forward:
  hand the health output to a Claude session.

### 5.1 The brain's automatic rollback and aux.db
OLD_SHA's code knows aux.db only up to schema 4. Its migrator refuses a newer file (on `main`:
`goldbot/db/migrations.py` `migrate` raises `SchemaVersionError`; the dashboard opens aux.db at start,
`goldbot/api/auth.py` line 335). `goldbot-deploy` now handles this itself (BACKLOG 37, the Linux version of
`vps_update.ps1`'s `Sync-AuxSchema`). OLD_SHA has no `compat_back_to` in its `migrations.py`, so on the way back the
script stops every service, steps aux.db 5 -> 4 as goldbot with every row kept, and starts them again. **Expect
`rolled_back`.** Check that this prints 4:
`sudo -u goldbot python3 -c "import sqlite3; print(sqlite3.connect('/opt/goldbot/state/aux.db').execute('PRAGMA user_version').fetchone()[0])"`

**Only if it still says `failed`** (for example aux.db is at a version the script does not know; it never changes
those): the supervisor, the engine, the scheduler and Telegram do not open aux.db on the old code, so trading and
alerts work. Check `journalctl -u goldbot-api -n 50`. If it shows `SchemaVersionError` for schema 5, step aux.db back
by hand with the same code the script runs:
```bash
sudo systemctl stop goldbot-api
cd /opt/goldbot && sudo -u goldbot -H /opt/goldbot/.venv/bin/python - <<'PY'
# the Linux equivalent of Sync-AuxSchema (goldbot/ops/vps_update.ps1 lines 75-103): schema 5 -> 4, every row kept
import sqlite3
conn = sqlite3.connect("/opt/goldbot/state/aux.db")
have = conn.execute("SELECT MAX(version) FROM schema_version").fetchone()[0] or 0
if have <= 4:
    raise SystemExit("aux.db already at schema %d: nothing to do" % have)
if have != 5:
    raise SystemExit("aux.db schema %d: only 5 -> 4 is known; left unchanged, ask for help" % have)
conn.execute("DELETE FROM schema_version WHERE version = 5")
conn.execute("PRAGMA user_version = 4")
conn.commit()
print("aux.db schema 5 -> 4 for the older release (rows kept; the next deploy re-applies 5)")
PY
sudo systemctl start goldbot-api
sudo systemctl start goldbot-deploy.timer
goldbot run health --baseline /opt/goldbot/logs/health_before.json ; echo "exit $?"
```
The step-back is safe:
* Migration 5 only added tables (`IF NOT EXISTS`).
* The new code kept `scheduler.json`, `agent_spend.json`, `telegram_outbox.json` and `agent_runs.jsonl` up to date,
  so the old code carries on.
* The next forward deploy re-applies 5 and keeps the rows.

### 5.2 Manual rollback after a deploy that succeeded (brain, ~5 min)
```bash
sudo goldbot-deploy --rollback <OLD_SHA>
```
It accepts OLD_SHA because it is an older commit of SHA on `main` that ran here (or passed CI). It takes the deploy
lock, waits for a pending entry, refuses while a scheduler job runs, and cancels a pending Telegram deploy approval.
Then it checks out OLD_SHA, rebuilds the dashboard, stops every service (inputs, the supervisor, engines last), steps
aux.db back 5 -> 4, starts the supervisor first and the rest after it, and checks every service for 90 s.
**Expect `rolled_back_manual: older version restored on the owner's request ...`**, also on Telegram.

If you switched on the minimum-lot exception (section 6), the first run is refused with
`settings.local.yaml does not validate with the target code (keys: risk.min_lot_risk_cap)`. Nothing has changed.
Either remove the line yourself and run it again, or let the script move it aside:
```bash
sudo goldbot-deploy --rollback <OLD_SHA> --drop-unknown-local-keys
```
The original file is kept as `config/settings.local.yaml.<UTC time>.bak`. Put the line back after the next forward
deploy (section 6).

If it says `refused ... GitHub can't confirm the floor`: GitHub did not answer (offline or rate limit). Wait a few
minutes and run it again, or treat it like the next case.

If it says `refused ... below the rollback floor`: the floor from 8.1 is set. Going below it re-opens code without
the auth hardening; that is your decision. Remove the floor only on purpose (`sudo rm /etc/goldbot/rollback-floor`),
roll back, and set it again afterwards.

If it says `rollback_reverted`: OLD_SHA was unstable too, and SHA runs again. Hand the journal to a Claude session.
Afterwards, in every case:
```bash
goldbot run health --baseline /opt/goldbot/logs/health_before.json ; echo "exit $?"
```
**What to expect after the rollback:**
* Telegram offers the newer version again. Tap **Skip** until the fix is merged.
* The old `config/accounts.yaml` has `vantage-demo` enabled, so health reports `engine:vantage-demo` with no
  engine. That is noise: no vantage engine runs on the brain.
* The old code has no minimum-lot exception, and it sizes in USD as GBP. On the small demo, 15m entries are refused
  (`min_lot_exceeds_risk`). That is the safe direction.


  goldbot-engine@icm-demo goldbot-api goldbot-telegram goldbot-news goldbot-scheduler goldbot-deploy.timer`. The copy holds OLD_SHA's schema (aux.db at 4), so this pairs with code
  at OLD_SHA. On code at SHA it simply migrates again.
* **Off-host:** RUNBOOK 0.6 "Restore after losing the brain", steps 2-5. The target is to be running again within 1
  hour.

## 6. Switch on the minimum-lot exception (brain only, ~5 min, after section 4 passed)

ADR 0004 decision 2; `config/settings.yaml` lines 58-64; `goldbot/config.py` line 101 accepts only values above 0

## 9. The gap week, 26-30 Oct: measure the clock, then switch only if it says so

ADR 0005; RUNBOOK "Server clock (US-EU DST gap weeks)"; `goldbot/ops/server_clock.py`. From Sun 25 Oct 01:00 UTC to
Sun 1 Nov 06:00 UTC, Athens time is UTC+2 and NY+7 is UTC+3. This is the only time the two can be told apart.

### 9.0 Before 26 Oct: have the switch ready (a Claude session, on your request)
Have a PR opened, CI-green and **not merged**, that changes:
* `config/accounts.yaml`: `server_tz: NY+7` for `icm-demo` and `icm-live` (lines 22 and 47), plus the header comment;
* `config/settings.yaml`: `brokers.icm.server_tz: NY+7` (line 17). The research swap prior uses that broker's
  rollover clock (`goldbot/execution/costs.py` `settings_swap`). Live trading reads `accounts.yaml`.
* an amendment to ADR 0005 recording the measurement.

`server_tz` is a tracked file on purpose: both boxes then get the same value from the same commit, and preflight
blocks when they differ. There is no supported local override. Do not edit `accounts.yaml` by hand on a box: the
next `goldbot-deploy` checkout would fail on the local change and roll back.

### 9.1 Measure (Mon 26 Oct, 08:00-10:00 UTC, market open; brain)
```bash
goldbot run preflight | grep -E 'time_sync|bridge_server_tz|server_clock'
goldbot run health | grep -E 'server_clock|engine:icm-demo'
date -u
```
`time_sync` must be ✅ first: a host clock that is off reads as a mismatch.

Then read the `server_clock:icm-demo` line:

| You see | It means | Do |
| --- | --- | --- |

| `ok ... server clock UTC+2 matches Europe/Athens` | The broker runs Athens time. | Nothing to switch. Close the NY+7 PR, and record the result in ADR 0005 and on issue #34. |
| `fail ... no known server zone explains it: host clock or feed` | Not a zone problem. | On both boxes run `chronyc tracking`: the offset must be well under 1 s. Check the feed. **Do not switch.** |

Post the `server_clock` line on issue #34. It holds no secret.

What a wrong zone means for exits until you switch:
* Stops and targets sit at the broker and are unaffected.
* The Friday weekend rule runs at 21:30 *server* time (`goldbot/engine/runner.py` lines 1481-1492). With Athens
  time configured and a broker on NY+7, it runs at 19:30 UTC on Fri 30 Oct instead of 18:30 UTC. That is still 1.5 h
  before gold's 21:00 UTC close.
* So the switch is not an emergency. Do it the same day, calmly.

### 9.2 Switch to NY+7 (both boxes, ~45 min, mostly waiting for CI)
1. Telegram: `/halt NY+7 switch`. Entries are already blocked; this keeps them blocked through the restarts. Exits
   continue.
2. Merge the 9.0 PR (release manager, or yourself on GitHub). Wait for CI to pass on the merge commit; that commit
   becomes your new SHA. `goldbot-deploy` refuses it before CI passes.
3. **Brain first:** `sudo goldbot-deploy <new SHA>`, or tap **Deploy** on Telegram's "New version ready". Brain
   first is the order that fails closed:
   * With the brain on NY+7 and the bridge still on Athens time, ticks read an hour in the future, so entries stay
     blocked.
   * The reverse order would make the probe read "ok" while the brain's session table and rollover are an hour off.
     Since BACKLOG 42 the engine also compares the bridge's zone with its own every 60 s and refuses entries with
     `bridge_incompatible` until the MT5 box is on the same zone; health fails `bridge_compat:icm-demo` meanwhile.
4. **MT5 box next:** `sudo goldbot-deploy <new SHA>`.
5. Check on the brain:
