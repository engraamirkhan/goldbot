- Health alerts and the outside dead man's switch no longer flap (owner 2026-11-04: "the health checks have been horrible ... up and down"; the emails came from the switch). Branch `fix/health-alert-flapping`:
  - Hysteresis (goldbot/ops/health.py `step_alerts`, `AlertPolicy`; settings `telegram.alert_confirm_polls` 3, `alert_confirm_min` 5, `alert_flap_note` 3): a check is told failing, and told recovered, only once the change held on 3 consecutive health passes AND for 5 min. A failure that clears inside the window sends nothing. The immediate list alerts on the first pass (`IMMEDIATE_NAMES`: kill_switch:, daily_cap:, weekly_cap:, order_failed:, backup_age, backup_prune, object_storage, bridge:, heartbeat:, engine:, engine_loop:; `IMMEDIATE_REASONS`: CRITICAL, terminal AutoTrading off, terminal on another account). bridge:, heartbeat:, engine: and engine_loop: are on it because each already waits before it fails: 5 min, 5 min, 45 min and 150 s. With engine_loop: on the list (SRE review MEDIUM), a dead or hung engine alerts in about 3 min. A check that failed and cleared inside the window 3 times in an hour gets one "flapping (not alerted)" line, at most hourly. Several changes still go out as one message.
  - state/health_last.json keeps `statuses` (the last report, still read by the deploy and daily-review checks) and adds `announced`, `pending` (kind, first_seen, polls), `flaps` and `flap_noted`. A file of the old shape loads with announced = statuses. `HealthWatch(state_dir)` without a policy keeps the old rule (every change at once) for the check-level tests; the Telegram service passes `AlertPolicy.from_settings`.
  - Dead man's switch (goldbot/ops/deadman.py): a daemon liveness thread (`start_liveness`) beats every min(60 s, half of `deadman_every_min`). It never waits on a health pass, so the monitor's period and grace no longer matter. It pings only on a health verdict: the first completed pass, or the last pass seeded from state/health_last.json when under 5 min old. Without one it sends nothing, so a service that crashes in every pass goes silent and the monitor turns down (SRE review HIGH). It keeps beating through a slow shutdown, so a deploy restart is not an email. The health pass only hands over its verdict (`observe`). `/fail` is sent for a confirmed failure (the same hysteresis or the immediate list), a Telegram alert undelivered on 2 passes in a row (SRE review LOW), or a verdict older than 5 min (`HEALTH_STALE_S`: a frozen pump, `health_checks_not_completing`). A transient FAIL pings ok and names the check in the body. `/start` is not used because it can only add emails. The owner has nothing to change on the monitor.
  - Alert log: aux.db migration 22 `health_alerts` (goldbot/ops/alert_log.py; ts_ns, channel telegram|deadman, kinds, checks) has one row per Telegram health message sent and one per state change the switch accepted (each change is one email). Count with `AlertLog(state).count_since(ts, channel=...)`.
